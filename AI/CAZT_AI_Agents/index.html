Conditional Access and Zero Trust for AI Agents

Secure enterprise AI agents running on AWS or Azure, with human identity services from Entra ID, Okta, Auth0, Curity, Ping Identity or another validated enterprise identity provider.
Use SPIFFE/SPIRE to verify workloads on supported systems, supported cloud identities for managed services, and CIBA or another secure workflow when a human must approve an action. Each deployment must verify its product capabilities and trust boundaries.

Core idea

Before an AI agent acts, establish who it is, assess what it intends to do, limit what it can execute, and apply the organization’s approval rules. These are the identity, semantic, execution and governance layers of CAZT.

The agent’s cloud host and the enterprise human identity provider are separate choices. SPIFFE/SPIRE gives supported workloads short-lived, attested identities; managed cloud services use their documented native identities. AWS IAM or Azure authorization controls access to cloud resources.

When a high-risk action exceeds the agent’s permissions, an authorized person must approve the exact operation. CIBA can support human authentication and consent through a compatible identity product; a secure alternative workflow can also work. The tool gateway must validate and enforce that approval before execution.

AWS or Azure hosting Enterprise IdP choice SPIFFE/SPIRE attestation Native cloud identities Semantic risk checks CIBA / human approval Exact-action enforcement Governance and audit

What this guide assumes

  • Choose where the agent runs and who manages user identities. Your agent can run on AWS or Azure, while Entra ID, Okta or another identity provider manages human sign-in. Cloud services separately control which resources the agent can access.
  • Use the identity method your hosting environment supports. SPIFFE/SPIRE verifies agents on supported systems you control. Managed services, such as Foundry Agent Service, use their supported platform identities. A gateway’s verified identity proves who the gateway is; it does not prove the identity of every agent calling it.
  • Ask an authorized person before a high-risk action goes beyond the agent’s permissions. CIBA can help authenticate that person and obtain consent. Your application must check that the approval covers the exact action, target and details before allowing it to run.
  • Check that your identity provider supports the approval method. See the dated Microsoft CIBA support assessment; use a supported alternative approval workflow or a separately integrated CIBA provider. Okta, Auth0, Curity and Ping offer documented CIBA options that require the right setup and enrolled users. A secure approval workflow without CIBA can also meet the requirement.
  • Protect the systems that issue identities and enforce approvals. Temporary credentials still depend on trusted issuers and protected signing keys. Secure those systems and make sure the agent cannot reach sensitive tools through a route that skips approval.
  • Verify the complete setup before using it in production. Features such as Conditional Access and identity federation work within specific product limits. Check availability, configuration and any preview restrictions. A matching decision-tree result suggests a suitable design; it does not certify that your deployment is secure or ready.

Four security layers for enterprise AI agents

The four CAZT layers work together throughout an agent’s task. They are complementary responsibilities, not checkpoints passed once. ATF’s five zero-trust elements describe protection objectives that span these layers.

Layer 1

Identity

Establish workload and applicable human identity, ownership, trusted run/task attribution and least privilege. Use SPIFFE/SPIRE on supported runtimes or documented native identities; govern enrollment, rotation and retirement. Identity proves who is acting, not whether an action is authorized.

Layer 2

Semantic controls

Assess proposed actions, prompts, retrieved content and outputs for manipulation, policy violations and data leakage. Combine intent validation with trusted behavioral signals; reassess changed actions. Semantic screening reduces risk and cannot grant authority.

Layer 3

Execution controls

Enforce PDP decisions at the tool PEP, segment resources, tools and networks, and constrain each operation. Monitor execution, block bypass paths and support effective stop controls, containment and rollback or compensating actions.

Layer 4

Governance

Define risk policy, data classification/provenance requirements, eligible approvers, identity lifecycle and evidence retention. Assign incident-response ownership and recovery criteria. Require exact-action human approval when high-risk actions exceed existing authority.

ATF zero-trust elements mapped to CAZT

Agentic Trust Framework (ATF) identifies five zero-trust elements: Identity, Behavior, Data Governance, Segmentation and Incident Response. These elements define protection objectives that span the four CAZT security layers described in this guide: Identity, Semantic, Execution and Governance. The mapping below is a high-level element mapping, not an ATF conformance crosswalk. ATF is an open specification published through the Cloud Security Alliance (specification v0.9.1, public review draft, April 2026; licensed CC BY 4.0; author Josh Woodruff, MassiveScale.AI). Its distinguishing mechanism is earned autonomy: four maturity levels (Intern, Junior, Senior, Principal) with five promotion gates and demotion criteria. Question 16 in the decision tree applies the maturity level alongside the autonomy and approval answers.

Layer 1: Identity layer

The identity layer should be grounded in existing cloud workload identity, not in overstated assumptions about agent-specific control planes.

Current baseline

What enterprises can do now

  • Azure-hosted agents: use system-assigned or user-assigned managed identities when the runtime is native to Azure.
  • External or SaaS-hosted agents: use service principals or workload identity federation when Entra-issued tokens are needed.
  • AWS-hosted agents: use runtime-scoped IAM roles such as Lambda execution roles, ECS task roles, EKS Pod Identity, or service roles.
  • Cross-cloud access: use federation and temporary credentials rather than embedded secrets.
Microsoft-specific caveats:

Microsoft Entra agent identity capabilities

This guidance applies to Microsoft Entra identities and policies. It does not describe AWS IAM, Okta, Curity or Ping controls; workload hosting alone does not determine which identity policies apply.

  • Microsoft Entra Agent ID is a Microsoft-specific agent governance capability. Verify current availability, licensing and supported controls for the target tenant before deployment.
  • It is Microsoft-specific and license-gated — not the universal identity baseline for all enterprise AI agents across platforms.
  • Separate application-only agent identity policies, agent-user policies and delegated-user policies. Do not apply human MFA to a workload. For supported managed-endpoint agent-user sessions, Microsoft documents device compliance and compliant-network controls using the Agent execution environments (Preview) condition. These are not application-only workload MFA controls. Microsoft scope documentation (updated September 30, 2026).
  • Application-only agent policies use documented block controls, including exclusions for approved identities/blueprints or security attributes; agent-risk blocking has its own feature status. Microsoft autonomous-agent policy guidance.
  • Endpoint prerequisites: the documented device-compliance scenario requires an Intune-managed Windows 365 Cloud PC for Agents; compliant-network controls additionally require the Global Secure Access client. Scope the preview execution-environment condition to endpoint sessions; these controls do not cover arbitrary AWS/Azure hosted agents.
  • Licensing: Microsoft’s October 6, 2026 reviewed documentation lists Microsoft 365 E7, or Agent 365 paired with at least Entra P1 or Microsoft 365 E3. Verify current tenant entitlement. Agent-user prerequisites and limitations.
  • Verify the current agent-risk feature status and license for the target tenant; preview/GA status must be dated and feature-specific.
  • Managed identities remain strong runtime identities, but they are not covered by Conditional Access for workload identities.
AWS-specific caveats:

AWS agent identities and resource access

  • Separate the AWS products and identities. An IAM role, a Bedrock Agents service role and an AgentCore workload identity have different jobs. A role does not automatically identify each agent instance or task; maintain trusted run attribution.
  • AgentCore Identity is AWS-specific. It provides workload identity and credential management, including OAuth tokens and API-key providers. It is not automatically SPIFFE attestation or an end-to-end secretless solution. Scope credential-provider access to the intended workload and user context.
  • Separate caller, runtime and tool permissions. Permission to invoke an agent must not imply permission for every tool action. Restrict service-role trust, iam:PassRole and action-group/tool roles; apply supported confused-deputy conditions for the actual AWS service.
  • Temporary AWS credentials are not per-action approvals. Task completion or a human denial does not automatically end an STS session. Enforce task expiry and approval at the tool PEP; test IAM deny/revocation and emergency containment paths.
  • IAM has its own policy model. Entra Conditional Access can evaluate the human Entra sign-in used to federate into AWS. It does not evaluate subsequent AWS API calls made with IAM role credentials; AWS IAM governs workload role assumptions and resource authorization. External IdP sign-in and CIBA consent do not automatically authorize AWS actions. Preserve least-privilege IAM and exact-operation approval independently.
  • Managed AWS hosting does not establish SPIFFE support. Verify the runtime before installing SPIRE. A gateway SVID identifies the gateway; managed agents require documented native credentials and verified caller/run context.
  • Check the selected AWS feature. Confirm region, API version, quotas and availability for Bedrock or AgentCore features. Do not assume native CIBA support merely because OAuth integration is available.

Layer 2: Semantic layer

Identity does not prevent an agent from being manipulated through language. The semantic layer is the defense against prompt injection, context poisoning, and unsafe tool selection.

Threats this layer addresses

  • Direct prompt injection and instruction override.
  • Indirect prompt injection through email, documents, knowledge bases, or web content.
  • Unsafe tool invocation caused by malicious or ambiguous instructions.
  • Unsafe output generation including data leakage and policy violations.

Realistic controls

  • Azure: Azure AI Content Safety, Prompt Shields, groundedness and safety evaluation patterns.
  • AWS: Amazon Bedrock Guardrails and explicit tool mediation around prompts and outputs.
  • Independent validation steps before tool invocation and before returning output to users.
  • Structured prompts, tool schemas, and retrieval filters that reduce ambiguity and blast radius.

The semantic layer should be treated as risk reduction, not as proof that the agent is now safe. It must be paired with execution constraints.

Continuous behavior and intent assessment

Compare proposed and observed operations with the authorized task, expected tools, resources, destinations, transaction limits and delegation scope. Detect patterns such as repeated denied calls, unusual privilege requests, unexpected data exports, tool sequences or activity outside the task window. Derive signals from verified execution records and trusted services, not solely from the agent’s description of its intent.

Send relevant signals to the runtime policy decision process. Depending on policy, deny the action, require eligible-human approval, narrow the request or initiate containment. Re-evaluate changed parameters and approval context before execution. Anomaly scores and model confidence cannot create authority; define thresholds, ownership and handling of false positives.

Layer 3: Execution layer

The execution layer is the final gate before an agent calls a tool or changes a resource. The tool service/gateway acts as the Policy Enforcement Point (PEP), consulting the authorization engine or Policy Decision Point (PDP). It enforces identity, task scope, policy decisions and any required human approval on AWS or Azure—even after prompts have passed semantic checks.

Containment controls

  • Ephemeral compute or isolated task runtimes.
  • Private networking and egress control.
  • Per-tool allow-lists and explicit action mediation.
  • Read-only filesystems where possible and scoped temporary storage.
  • Resource quotas, circuit breakers, and rollback design.

Task-scoped authorization, stated correctly

  • Task-scoped permissions are a valid architectural target.
  • In practice they are usually built through orchestration logic, policy engines, ephemeral credentials, and approval workflows.
  • They should not be presented as though a single cloud-native “TBAC” feature already exists universally across platforms.
  • Use them as a design pattern: scope identity, tool access, transaction range, and time window to the active task.
TBAC (Task-Based Authorization Controls) originates from Thomas & Sandhu, IFIP WG11.3, 1997 — it is an academic access-control model, not a NIST/ISO standard or productized cloud feature. Note: “TBAC” is also used in industry for “Time-Based Access Control” (JIT, time-boxed grants) — a distinct concept sharing the acronym.

Execution security is where Zero Trust becomes operational: never assume the agent should retain standing access once the current task step is complete.
Cloud-native

AWS STS — temporary credentials with task restrictions

AWS STS AssumeRoleWithWebIdentity vends temporary credentials with a minimum duration of 900 seconds (15 minutes). Session policies (inline Policy parameter or managed PolicyArns) can further restrict the assumed role’s permissions to only what the current task requires — session policies can only reduce, not grant.

Use STS for validated role-assumption profiles. Task authorization may expire before the cloud session; enforce task deadlines independently at the PEP.

Emerging standard

Model Context Protocol (MCP)

Use the pinned HTTP authorization profile described in Protocol and deployment requirements: flow-specific OAuth, protected resource metadata, audience binding and no token passthrough. Local STDIO requires separate process and credential controls.

CIBA-backed execution: pause, approve, enforce

  1. Pause: a semantic policy decision of “approval required” creates a durable pending operation. Do not execute while awaiting human intervention.
  2. Authenticate and obtain consent: the approval service uses the selected provider’s supported CIBA integration, or a secure alternative human workflow. For Entra, follow the dated CIBA support assessment and choose a supported alternative or separately integrated CIBA provider.
  3. Bind: record authorization for the exact requested operation. A successful human login or CIBA token alone is insufficient.
  4. Revalidate: verify approver eligibility, current policy, workload/run identity, parameter digest, task status and expiry immediately before the tool acts. Denial, timeout or missing evidence blocks execution.
  5. Execute once: consume the approval atomically and execute with the tool’s least-privilege identity. Audit completion/failure; recovery requires safe retries, reconciliation and any renewed approval.

CIBA calls belong in a protected approval service, not in this browser SPA. Pending approval must not require an agent process to wait indefinitely; resume through an authenticated task handle and recheck all controls.

SPIFFE/SPIRE at execution boundaries

  • Verify SVIDs and authorize the SPIFFE ID for the specific tool operation; mTLS establishes peer identity, not permission for every action.
  • Protect the Workload API socket, isolate workloads and registrations, support credential rotation and trusted bundle updates, and reject untrusted domains/audiences.
  • Keep service identity separate from instance/run attribution. Bind approval to independently verified run context, especially when replicas share a SPIFFE ID.
  • Across gateways, propagate integrity-protected identity/context with explicit trust mapping. Never accept agent-supplied identity headers as proof or claim the gateway’s SVID attests a managed agent.

AWS and Azure enforcement

  • AWS: constrain agent invocation roles, runtime roles and tool/service roles separately. IAM/STS resource permissions complement exact-action approval; an Okta or Entra human token does not replace AWS credentials.
  • Azure: use documented Entra workload tokens and least-privilege Azure RBAC for Azure resources, even when Okta or another vendor provides human identity. OAuth consent does not grant unrestricted tool access.
  • Managed agents: route consequential Foundry, Bedrock or AgentCore tool actions through an enforceable gateway/tool PEP using supported authentication. Disable high-risk actions if trusted identity/run correlation or approval enforcement cannot be established.
  • Cloud sessions: test emergency IAM deny/revocation or Azure containment paths. Enforce shorter application task deadlines independently; do not rely on token expiry or stopping a process to undo completed actions.

Execution evidence and acceptance checks

Correlate the workload principal, trusted run/task identifier, policy decision, human approver, approval identifier and actual tool result. Join application evidence with CloudTrail or Azure resource logs where available; do not log tokens, private keys or sensitive payloads.

Before enabling high-risk tools, test wrong identity/audience, expired approval, wrong approver, changed arguments, replay, concurrent consumption, provider timeout, task cancellation, direct bypass and failures after partial execution. Set transaction limits, circuit breakers, kill switches and compensating actions appropriate to the tool.

Tooling

Policy-as-Code authorization engines — the PDP

Policy-as-Code expresses authorization rules in a form software can evaluate. The authorization engine normally acts as the Policy Decision Point (PDP). It decides whether a specific operation is permitted. The Policy Enforcement Point (PEP), usually the tool service or tool gateway, enforces that decision before execution. These roles can share an application, but they remain distinct responsibilities.

TermImplementation in this guideResponsibility
PDP — Policy Decision PointAuthorization engine / policy serviceEvaluate verified identity, action, resource, task context and approval evidence against current policy.
PEP — Policy Enforcement PointTool service / tool gateway / executor authorization boundaryRequest and enforce the decision before side effects; reject missing or invalid evidence and prevent bypass.
PIP — Policy Information PointTrusted context sourcesSupply verified attributes such as workload/run identity, resource ownership, risk classification and approver eligibility. Agent-supplied assertions alone are not trusted evidence.
PAP — Policy Administration PointGoverned policy management and deployment processAuthor, review, version, test and distribute rules. CI/CD can support this role; runtime evaluation does not take place only in the pipeline.
Approval serviceHuman approval orchestratorInitiate CIBA or an alternative workflow, validate the human result and create/store exact-operation approval evidence. It is not automatically the PDP or PEP.

Runtime example: an agent requests a firewall change from the tool service (PEP). The PEP asks the authorization engine (PDP), using verified context from trusted sources (PIP). If application policy requires human approval, the approval service obtains it; the PEP requests a fresh decision and executes only the approved change. Some engines return permit/deny only; the application implements the “approval required” workflow around those decisions.

Deployment: on AWS, host a compatible policy service on EKS/ECS/EC2 or embed it in the tool application; on Azure, use AKS/VMs or supported application hosting. Place the PEP in the actual tool execution path. An API gateway may perform some enforcement, but model-endpoint access control alone does not govern downstream tool actions. Validate the chosen engine’s runtime support.

CI/CD versus runtime: the pipeline tests and deploys policy; the PDP evaluates requests and the PEP enforces decisions while the agent runs. Failed or unavailable required authorization checks must block consequential execution. Cache decisions only within explicit limits tied to identity, action, parameters, policy version and expiry.

Policy-as-Code tools for agent authorization include:

  • Cerbos — YAML policies with CEL expressions.
  • OPA / Rego — general-purpose policy engine widely adopted in Kubernetes and service-mesh deployments.
  • Cedar — open-source policy language/engine; Amazon Verified Permissions is an AWS managed service using Cedar.
  • Polar — Oso’s logic-based policy language; the original library is deprecated, while Oso Cloud is a separate service.

These tools evaluate authorization requests in real-time against declarative policies that encode ABAC, ReBAC, and TBAC rules.

Segmentation and incident containment

Separate production from test, tenants from one another, and agent runtime permissions from tool-executor permissions. Apply resource, network/egress and tool allowlists with argument validation. Ensure sensitive resources cannot be reached through alternate credentials, tools or network paths that bypass the PEP.

On an incident signal, the execution service can suspend new tool calls, cancel queued operations and invalidate unconsumed approvals. Apply tested AWS IAM/session restrictions or Azure access/network containment as appropriate, and isolate affected workloads. Confirm containment at the resource side; stopping a process or waiting for token expiry is insufficient. Use rollback or compensating actions for completed side effects.

Layer 4: Governance layer

High-impact agent actions should not be described as if there is a single turnkey “step-up token” feature for every case. Governance is usually implemented as a composed workflow.

What governance should cover

  • Financial actions above a threshold.
  • Destructive data changes.
  • Privilege grants and identity changes.
  • Security policy or network policy modifications.
  • Bulk export or cross-boundary movement of sensitive data.

How to phrase the control model accurately

  • Use Conditional Access, authentication context, PIM-style elevation, or custom approval workflows where supported.
  • Describe the end state as a governed approval pattern, not as a universal built-in agent authorization mechanism.
  • Preserve strong evidence: who approved, what context was reviewed, what changed, and for how long.
  • Ensure approval grants are time-bound and tied to a narrow action set.
Important caveat: authentication context, PIM-style elevation, and MFA-based step-up apply to USER identities, not to agent/workload identities. Service principals cannot satisfy interactive authentication challenges. For workloads, use provider-supported identity policy, custom approval workflows, scoped short-lived credentials and independent policy-engine gates. Entra service-principal workload policies, Agent ID application-only policies, delegated-user policies and agent-user policies have distinct scopes; managed identities are outside workload Conditional Access.

Do not imply that every governance flow is natively cryptographic and automatic. In many enterprises, the secure implementation is a composite of IAM, approval workflow, orchestration logic, and logging.

Data governance across retrieval, execution and output

Define data owners, authoritative sources, provenance metadata, classifications and permitted purposes. Validate source integrity and access rights before retrieval; treat retrieved instructions as untrusted content. Carry trusted sensitivity and tenant context into policy decisions, minimizing data sent to models, tools and other organizations.

The execution PEP enforces resource and destination permissions; semantic checks inspect content and outputs for leakage and unsafe instructions. Apply appropriate redaction, DLP, output review, retention and deletion controls. Provenance supports traceability but does not prove content is truthful or safe. Record necessary evidence without logging credentials or unnecessary sensitive payloads.

Incident response and safe recovery

  1. Detect and triage: correlate identity, run/task, policy, tool, cloud and human-approval events; identify the affected agent, resources and accountable responders.
  2. Contain: block consequential execution at the PEP, invalidate pending approvals, restrict resource access and isolate affected runtimes. Verify the actual stop and containment effect.
  3. Investigate and remediate: preserve controlled-access evidence, inspect compromised identities, policy, source content and tool behavior; rotate or retire affected credentials and trust bindings where necessary.
  4. Recover: restore known-good policy/runtime state, roll back or compensate for side effects, revalidate permissions and require fresh approval for resumed gated operations.
  5. Review: document impact and lessons, improve detection and runbooks, and meet applicable notification and retention obligations.

Assign incident commander, technical responders, data owners and recovery approvers. Define escalation thresholds, response targets and separation of duties; exercise denial, replay, credential compromise, approval-service outage and resource-bypass scenarios. Human approval is an authorization control, not a substitute for incident response.

SPIFFE/SPIRE workload identity foundation

Attested workload identity: purpose, trust boundaries and integration with enterprise identity and cloud authorization.

What SPIFFE and SPIRE provide

SPIFFE defines workload identities and verifiable identity documents (SVIDs). SPIRE implements node/workload attestation and short-lived SVID issuance through the Workload API. Use X.509-SVIDs for mTLS and audience-bound JWT-SVIDs where the recipient supports them. Deploy on supported AWS EKS/EC2 or Azure AKS/VM environments; use native identities at managed service boundaries. Enterprise human IdPs, cloud authorization and exact-action approval remain separate controls.

Resolving the bottom turtle

Use independently verified platform/node evidence and local workload selectors to obtain identity through the Workload API, without an application-held bootstrap password. Protect the signing authority, administrative registry, authentic bootstrap bundle, node OS and orchestrator. SVID private keys and bearer tokens remain secrets. Hardware protection is optional and configured explicitly; production join tokens are not the preferred bootstrap.

Authentication and action authorization

Use X.509-SVIDs for SPIFFE-aware mTLS; verify certificate chain, expiry, exactly one SPIFFE URI SAN and expected peer. For JWT-SVIDs, verify signature, permitted algorithm, trusted issuer/keys, SPIFFE subject, narrow audience and expiry. Bind the authenticated principal to trusted instance, run, tenant, task, parent/delegating user and approval context. Model intent and confidence cannot grant authority.

At the tool boundary, intersect workload permissions, task grant, applicable user authority, resource policy and conditions. Use Permit, Deny and Approval required consistently. If policy requires narrower parameters, return obligations and evaluate the revised operation again before permitting it. Bind approval to exact operation/resource/argument digest, principal, task, expiry and a single-use nonce. Child delegation may only narrow scope. Block alternate tool/cloud credential paths.

AWS deployment and cloud federation

For supported EKS/EC2 execution, deploy SPIRE Server with protected keys and durable storage, node Agents, narrow registration selectors and restricted local sockets; use SDK/SDS credential refresh. Validate platform attestation and plugin support for the pinned release. Do not assume managed/serverless runtimes can host a SPIRE node Agent.

Choose federation according to the target resource. For AWS-hosted workloads accessing Entra-protected APIs, a documented federation pattern to validate is SPIRE JWT-SVID → Entra workload federation → Entra-issued resource token. For AWS resources, use native IAM roles or configured SPIRE OIDC → AWS STS federation. An Entra federated identity credential does not establish AWS STS compatibility. Azure-hosted applications similarly use supported native identity or verified workload federation for Azure APIs. Enterprise human IdP selection is independent of these workload paths. Microsoft workload federation · SPIFFE federation guidance. Product documentation does not establish that this deployment has passed integration testing.

Lifecycle, containment and acceptance

Choose measured SVID lifetimes; test live rotation, bundle/key rollover, HA, clock skew and recovery. Removing registration prevents future issuance but does not instantly revoke issued SVIDs or cloud sessions. Deny affected identities/tasks at PEPs, terminate connections and isolate compromised nodes. Fail closed for expired identity or unavailable required policy/approval services.

  • Reject wrong node, selectors, peer, trust domain, audience and expired or forged SVIDs.
  • Reject valid identities with unauthorized actions, widened delegation or replayed/changed approval.
  • Test cloud exchange negative cases, workload isolation, renewal/outage behavior and end-to-end containment delay.
  • Revoke replaced passwords/API keys and prove no bypass path remains; record legacy broker exceptions.

CIBA and human step-up authorization

Client-Initiated Backchannel Authentication (CIBA) enables a backend client to initiate human authentication and consent on a separate authentication device. It is defined by OpenID CIBA Core 1.0, an OpenID Foundation specification, not a standalone IETF RFC. It is an optional protocol choice for the required approval workflow.

Policy for high-risk agent actions

In this CAZT profile, a high-risk action exceeding the agent’s existing authority requires explicit approval by an eligible human before execution. Any pre-authorized exception requires an explicit governance policy. Approval does not confer broad administrative authority. Human step-up authentication, action authorization and workload authentication are separate controls.

Common approval sequence across deployment patterns

  1. The agent presents a valid SVID on an attested runtime, or its documented native workload credential to the tool gateway/PEP. The gateway verifies the applicable issuer/trust domain, identity and audience; native callers are not represented as SVID holders.
  2. The semantic policy decision requires approval. The approval service creates a pending operation with a digest of canonicalized action parameters.
  3. Use the deployment’s enterprise human IdP: Okta, Curity, PingFederate or Auth0 can supply their documented CIBA flow. With Entra enterprise identity, integrate a separately verified CIBA service or a supported non-CIBA approval workflow. Enrollment/federation must work for the chosen authenticator; cloud hosting does not determine the CIBA provider.
  4. The approval service acts as the registered CIBA client, identifies the eligible approver and initiates the request. The human sees the exact operation in a trusted approval UI and authenticates/consents. The service retrieves and validates the result using the provider’s supported delivery mode.
  5. The approval service issues or stores a tamper-protected, short-lived, single-use authorization bound to the verified workload principal (SPIFFE ID or native identity), verified run/task identity, human subject/issuer, operation, resource, parameter digest, policy version, expiry and nonce.
  6. The AWS- or Azure-side tool PEP atomically consumes the approval only for that operation, rechecks policy and records the decision/execution audit correlation. No execution occurs on failure or expiry.

Authenticating the user is not proof that the user approved these exact parameters. A CIBA binding_message helps correlate the interaction; it is not by itself a cryptographic transaction authorization artifact. Prevent approval fatigue, enforce request limits and apply dual approval where governance requires it.

Does SPIFFE/SPIRE support CIBA?

SPIFFE/SPIRE does not implement human CIBA authentication or issue CIBA user tokens. The protocols are architecturally complementary: use SVID-authenticated connections between the agent, gateway and approval service; use CIBA between the approval service and the human identity provider. This is a proposed composition, not a vendor-certified interoperability claim.

Direct X.509-SVID OAuth mTLS client authentication requires explicit authorization-server certificate trust, client registration, identity mapping and rotation support. A JWT-SVID is not automatically a private_key_jwt client assertion: its subject, audience and claims have different semantics. SPIRE OIDC discovery exposes verification metadata; it does not transform an SVID into a user login or CIBA assertion.

For the secretless objective, require tested asymmetric client authentication or a supported identity broker for the CIBA client, with protected keys and rotation. Do not silently introduce a static client secret because a vendor tutorial uses one. If unsupported, record the residual credential exception and migration plan. SPIRE still needs protected trust roots and signing keys; secretless agents do not mean an architecture without cryptographic keys.

Protocol and deployment requirements

Human approval and identity-policy scope

CIBA poll/ping/push specify client notification/token delivery. They do not define biometrics, autonomy or approval volume. FAPI CIBA excludes push. CIBA authentication does not itself bind approval to a transaction. Entra, Okta, Curity and Ping require their own supported authentication and approval integration; see the dated Microsoft CIBA assessment.

MCP authorization — pinned baseline 2025-11-25

Authorization is optional in the protocol. Where enabled for HTTP transports, use protected resource metadata (RFC 9728), resource indicators (RFC 8707), token audience validation and no token passthrough. Apply authorization-code PKCE to user-delegated code flows; use supported workload authentication for app-only access. Existing pre-registration comes first, supported Client ID Metadata Documents next, then supported DCR fallback. STDIO uses a separately secured local credential/process boundary.

Federation acceptance gates

Expose the SPIRE OIDC Discovery Provider via authentic HTTPS with discovery/JWKS reachable by Entra, not SPIRE administrative APIs. Validate key rollover and availability. Match Entra FIC issuer, subject and audience exactly, including case; typically request the api://AzureADTokenExchange audience. Check current per-application FIC limits before adopting per-instance subjects. AWS OIDC role trust must pin issuer/provider and expected aud/sub. ExternalId applies to appropriate third-party AssumeRole profiles, not AssumeRoleWithWebIdentity.

Task duration and policy engines

Enforce task deadlines at the PEP even while cloud credentials remain valid. AssumeRoleWithWebIdentity has a 900-second minimum; its credentials are not automatically bound to a single tool call. Cedar is a language/engine; Verified Permissions is the AWS managed service. Polar is a policy language; the original Oso library is deprecated, while Oso Cloud is a separate service.

Cross-cloud security

Cross-cloud agents introduce real confused-deputy and trust-boundary risks. The underlying problem is real, but trust policies must be described using documented cloud patterns.

What is valid to say

  • Azure-hosted or federated agents that access AWS need carefully scoped AWS trust and authorization boundaries.
  • Confused deputy protection is relevant when one system can act on behalf of another across trust boundaries.
  • AWS documents the use of aws:SourceArn and aws:SourceAccount for confused-deputy mitigation in appropriate AWS service contexts.
  • CloudTrail and equivalent logs should be used to monitor role assumptions and anomalous access paths.

What to avoid

  • Do not invent AWS ARN formats for Azure application identities.
  • Do not imply a generic Azure-app-to-AWS-role trust policy pattern that AWS officially documents if it is not actually documented.
  • Do not overfit confused-deputy guidance that is intended for AWS cross-service scenarios into unsupported cross-cloud examples.

Recommended cross-cloud pattern

Use standards-based federation and short-lived credentials in each cloud, then enforce resource-side least privilege, logging, and approval for high-risk actions. Keep the trust relationship explicit and minimal. Treat the agent as an external workload from the perspective of the target cloud unless it is natively hosted there.

The correct architectural emphasis is federation + temporary credentials + least privilege + auditability, not custom identity translation logic.
Emerging patterns

Decentralized identity for cross-organizational agents

For future cross-organizational agent scenarios where centralized identity providers are insufficient, emerging patterns include:

  • W3C Decentralized Identifiers (DIDs v1.0) — self-sovereign identifiers decoupled from any single provider.
  • Verifiable Credentials (VC Data Model v2.0) — cryptographically signed claims exchangeable across trust boundaries.
  • Zero-Knowledge Proofs (Data Integrity BBS Cryptosuites) — selective disclosure of attributes without revealing the underlying claim set.
DID Core and the VC Data Model are W3C Recommendations. Their suitability for autonomous agent-to-agent trust still requires implementation-specific assurance; they do not automatically replace federation. They may, however, become relevant for decentralized agent ecosystems where bilateral federation is impractical or where no single trust anchor is acceptable to all parties.

High-risk action sequence

  1. The AWS agent authenticates to the tool PEP with its verified workload identity. The PEP resolves trusted task/run context.
  2. The authorization engine (PDP) evaluates the proposed operation and semantic risk context against governance rules to determine whether eligible human approval is required.
  3. The approval service initiates CIBA with Okta. The approver reviews the exact action on the trusted approval interface and authenticates/consents using the enrolled Custom Authenticator. The service polls and validates the CIBA result.
  4. The service binds authorization to workload identity, human issuer/subject, task, operation, target, parameter digest, policy version, expiry and single-use nonce.
  5. The execution PEP rechecks policy and consumes that authorization only for the approved operation. The tool executor uses its own narrow AWS role; the agent lacks permissions to bypass the tool gate.

A CIBA user token is neither an AWS access key nor an automatic permission to assume a workload role. A SPIRE JWT-SVID is not an Okta user token. Keep Okta user identity, SPIFFE workload attestation, AWS role credentials and application approval artifacts distinct.

Four-layer mapping

Governance defines risk and eligible approvers. Semantic returns approval required for the concrete action. Identity combines separately verified SPIFFE/native workload identity and Okta human authentication. Execution pauses, validates and enforces the exact approval before side effects.

Use CloudTrail for AWS API activity and correlate it with application decision/execution records and Okta authentication events. Record trusted identifiers and approval status without logging credentials or tokens. Test denied/expired approval, wrong approver, changed arguments, replay, issuer/audience mismatch, key rotation and direct-resource bypass.

Curity, PingFederate or Auth0 can occupy the external enterprise human IdP/CIBA role using their own documented configuration; this is not a claim of interchangeable vendor capabilities or certified end-to-end interoperability.

CAZT placement and bypass prevention

  • Governance: approve vendor trust, identity mappings, eligible approvers, data residency and any preview or credential exceptions.
  • Semantic: evaluate each proposed tool operation; require human approval when a high-risk action exceeds existing authority.
  • Identity: validate the external human identity separately from the Azure native workload identity or attested SPIFFE identity. Correlate run/task identity without trusting agent-supplied claims.
  • Execution: enforce an exact-operation, expiring, single-use approval at the tool service. Restrict direct resource access so the agent cannot bypass the gate. A model-inference gateway alone does not govern downstream tool side effects.

For managed Foundry tool calls, use the supported tool authentication path to reach the PEP. If that path cannot carry a trusted run identity or enforce approval, disable the high-risk tool until an enforceable integration is implemented. Do not assume a paused agent run can wait indefinitely; use a durable pending operation and revalidate policy before resuming.
